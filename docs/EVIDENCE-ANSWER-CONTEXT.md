# Evidence answer context v1

This new offline wrapper is an experiment candidate prompted by the separate parent audit of the completed known-topic evidence pilot. The audit found a language-boundary error, blurred attribution of a project-authored English rendering to its upstream edition, and unnecessary repetition of source metadata. The frozen pilot, its answers, reviews, receipts, delivery module, private chat, and provider code remain unchanged.

`bibleprep.evidence_answer_context.build_model_input` accepts an existing system prompt and question plus the verified bundle, current registry, and exact notice manifest. It returns the established three text fields: `system_prompt`, `question`, and `evidence`. The question is unchanged. Versioned generic guidance is appended to the trusted system prompt. The evidence field is exactly the complete result of `evidence_delivery.render_model_input`, so downstream request preparation continues to quote it as source data rather than trusted instructions.

The wrapper calls the existing renderer on every valid invocation. That path regenerates the candidate from current records, source bytes, registry decisions, scholarly review bindings, and notice manifest; it does not accept a cached approval. Any stale or changed dependency fails closed. The wrapper has no transport, credential, environment, command-line, registry variant, chat integration, or model call.

The v1 guidance tells a future model to answer in plain English while preserving the project's intent-based reflection behavior. It distinguishes original representations from supplied English renderings, binds supplied-rendering attribution only to an explicit `rendering_author`, and lets the model provide its own clearly identified rendering without presenting supplied English as newly translated. It instructs the model not to expand claim or language scope from citation locators and checked ranges and treats record-wide coverage limits as caution rather than positive evidence. It retains uncertainty and edition/manuscript distinctions, requires explicit support from the selected text, annotation, or correctly attributed rendering before describing a statement as grounded, and keeps internal identifiers and rights boilerplate out of ordinary conversational prose when they are not needed. Accompanying source notices remain byte-for-byte present in the evidence field.

All nested evidence values remain untrusted data, including author, claim, citation, limitation, and notice strings that resemble instructions. The guidance is deliberately generic: it contains no pilot answer, passage-specific rule, verse identifier, or source-specific correction.

A future evaluation coordinator can call this wrapper when constructing each packet or lookup slot's `model_input`, before the unchanged native request preparer processes that three-field object. This document does not authorize integrating it into the current coordinator or private chat. It also does not show that the completed pilot answers are fixed, approve promotion to chat, establish scholarly accuracy, or authorize training. A fresh-source-family evaluation must be frozen before this candidate is used to support a quality claim.


## Offline verification and next comparison

Four new focused tests passed; the worker also ran the existing delivery and request tests for eighteen scoped compatibility checks in total. The parent separately checked the four Bible inputs from the completed pilot against the current six-component source registry and exact notice manifest. Every evidence block, source notice, original-language character and question remained unchanged. The trusted guidance added 363 native input tokens per case; totals ranged from 2,931 to 3,989, below the 8,192-token input ceiling. These were cached local rendering checks, with no provider request or answer generation. All 112 previously bound implementation and private pilot files remained unchanged.
