# Publication and privacy practices

The owner intends an open-source public project and wants personal data excluded. Prepare a shareable repository from the outset even while development is private. The public [Meforash repository](https://github.com/rowant-labs/meforash) has been created. The first reviewed source commit was published on September 11, 2026; private runtime assets remain excluded.

## Public project material

Code, authored documentation, cited decision records, source manifests and license notices, preparation recipes, training configurations, synthetic/permissioned evaluation examples, aggregate results, and release notes belong in the public project. Include a model card for each published adapter with the base revision, training data description, tests, limitations, and intended uses.

Code and authored documentation use Apache-2.0. Third-party source texts, annotations, translations, and weights retain their licenses. Check whether each data and adapter artifact can be distributed before attaching it to a release. Import scripts and manifests can be shared without bundling uncleared material. Do not describe a partially reproducible release as fully reproducible.

## Private material

Keep credentials, environment files with secrets, production databases, raw conversation logs, account identifiers, private notes, personal filesystem paths, and unreviewed training/export artifacts out of commits. Root-level research notes from the planning conversation remain local; shareable versions live in docs. Use placeholders in sample configuration and use constructed examples in screenshots and demonstrations.

Do not collect or retain conversational content merely to make the project open source. Do not train on user conversations by default. If conversation history is later offered, specify its storage, retention, deletion, and provider processing separately. Any voluntary data contribution must be explicit and reviewed; open-source code does not make users' conversations public.

## Before the first push or a visibility change

Review the exact files and full commit history, including branches, tags, notebook outputs, author metadata, logs, attachments, and release artifacts. Use secret scanning and human review for personal information; a credential scanner does not establish that ordinary personal data is absent. Check documentation for local account paths and screenshots for private information.

Ignored files are not automatically safe: ignore rules do not remove tracked files or erase earlier commits. If a credential is exposed, revoke or rotate it; history cleanup alone is insufficient. A private repository is not a place to commit secrets in anticipation of deleting them before publication. [GitHub secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning), [repository visibility](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)

Preserve a clean decision history so the public can follow the reasoning without receiving personal conversations. Prefer a privacy-preserving commit email before creating the first public-facing commit. Do not claim that hosted secret scanning or push protection has been enabled until the actual repository settings have been checked.

## Release record

Each release should identify what was published, its license, model/source versions, evaluation results, limitations, privacy/rights checks performed, and any reproducibility gaps. Experimental results should include failed or inconclusive findings when they bear on the released model's claims.
